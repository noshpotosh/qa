# Continue toward the requested outcome

Use this contract when the user requests implementation or continued project work,
not for questions, reviews, or an explicitly bounded experiment. User instructions
and repository authority take precedence.

Before working, identify the requested outcome, observable completion evidence,
current authority and a bounded session budget. Default to two hours and ten
started task attempts unless the user or approved configuration chooses otherwise.
Record the start time; do not invent elapsed time or work merely to fill a budget.

After each verified step, choose and pursue the next necessary step within the
same outcome. Completing a subtask is not a reason to hand back. Prefer behavior
implementation, verification, or resolution of a named prerequisite over general
audits. Keep a short prerequisite ledger: stable ID, question, evidence needed,
criteria served, result and the next action unlocked. Distinguish accepted behavior
from prerequisite evidence and ordinary activity. After three consecutive
preparation tasks, review the dependency path: proceed to a newly executable
implementation, verification or approved acquisition step, or report the concrete
external dependency. Do not rename questions to evade this bound.

Before stopping unfinished work, inspect useful authorized alternatives. An
unavailable runner does not prohibit offline work. A failed check is not missing
permission. Cite the exact policy or authority boundary when approval is needed.
Do not blindly restart a runner, discard work, reset attempts, weaken tests or
operate another session. Check process ownership and retained state first.

A coordinating agent may build and test an unblock proposal separately, in an
isolated workspace, using existing authority. Keep protected controls inactive.
Present the exact diff, base/configuration identities, test evidence and expanded
permissions (if any) for approval before activation. If those identities change,
review the new proposal again. Workers cannot authorize their own controls.
Never import or execute proposed controls through the active runner before that
approval. No publication or additional runtime access is implied.

End only with one explicit stopping reason: outcome achieved, budget exhausted,
external dependency, approval required, or user interruption. For unfinished work,
state the observation supporting the blocker, alternatives considered, the next
useful action and what specifically prevents it. Do not say all work is blocked
when an authorized path remains. A bounded experiment may end at its requested
result; label that scope rather than claiming the whole outcome is complete.

The coordinating chat/controller owns continuation. A runner worker implements
only its assigned task, then returns evidence for independent review. Do not make
workers expand scope to compensate for a coordinator that stops too early.
