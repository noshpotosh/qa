# Project Presentation

## Rules
- PRES-01: a newcomer should find the problem, current capabilities, setup and one useful demo path. Missing pieces are suggestions unless a stated working path is broken.
- PRES-02: screenshots and links should reflect the current implementation; label prototypes and limitations honestly.
- PRES-03: explain one or two consequential architectural tradeoffs with evidence or linked decisions; avoid claims such as production-ready without acceptance evidence.
- PRES-04: distinguish personal contributions from upstream or third-party work; retain attribution and license notices.
- PRES-05: optimize for understandable engineering evidence, not badges, contribution counts or manufactured history. Do not promise recruiter outcomes.

## Examples
Bad: an attractive screenshot with no run instructions and an unsupported production-ready label.
Good: a short problem statement, reproducible demo, tested capabilities, architecture decision and known limitations.

## Review contract
Review and prepare recommendations only. Repository policy and the requested scope take precedence. Do not edit code, rewrite history or publish messages from this skill. Report evidence-backed findings with rule ID, severity (blocking or suggestion), location, evidence and a concrete fix. Blocking is a finding severity, not automatic merge authority. Skip duplicate mechanical findings. State unavailable checks explicitly.
